# Почтовый AI-агент

«Почтовый AI-агент» — CLI-приложение для работы с перепиской
компании по поставке промышленного оборудования и комплектующих.
Приложение ищет письма, читает цепочки, дополняет их справочным контекстом,
готовит сводки и сохраняет ответы как черновики в SQLite. Отправка писем не
реализована.

Основной проверенный провайдер — локальная Ollama. Официальный OpenAI Python SDK
используется как клиент OpenAI-совместимых Responses API и embeddings API.

## Архитектура

```text
Git Bash CLI
    ├─ Settings ── переменные окружения
    ├─ SqliteEmailRepository ── письма, цепочки, черновики
    ├─ MailTools ── search_emails, read_thread, create_draft
    ├─ ChromaContextStore ── обязательный внутренний RAG
    ├─ OpenAILlmClient ── OpenAI-совместимый Responses API
    └─ MailAgent
         LLM response → CanaryGuard → Python-валидация → инструмент/результат
```

`MailAgent` предоставляет модели инструменты поэтапно. Python-код проверяет
доступность инструмента, аргументы, выбранную цепочку, обязательный RAG,
разрешение на черновик и получателя. Содержимое писем и документов считается
недоверенными данными, а не инструкциями.

## Технологии и модели

- Python 3.12;
- SQLite;
- ChromaDB с cosine distance;
- Pydantic;
- официальный OpenAI Python SDK;
- Ollama `qwen3:8b` для LLM;
- Ollama `embeddinggemma` для embeddings;
- Pytest и Ruff.

## Установка на Windows 11 в Git Bash

Установите Python 3.12 и Ollama для Windows. После запуска Ollama проверьте CLI
и загрузите обе модели:

```bash
ollama --version
ollama pull qwen3:8b
ollama pull embeddinggemma
ollama list
```

В корне исходного репозитория создайте окружение и установите проект в editable
режиме:

```bash
python -m venv .venv
source .venv/Scripts/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

Проверенный способ запуска предполагает наличие каталогов `data/` и `prompts/`
в исходном репозитории. Standalone wheel в текущей версии не поддерживается.

## Конфигурация

Приложение использует следующие переменные окружения:

| Переменная | Назначение | Обязательность |
|---|---|---|
| `LLM_API_KEY` | Ключ API; для локальной Ollama подходит техническое значение | Для `index-context` и `run` |
| `LLM_MODEL` | Модель Responses API | Для `run` |
| `LLM_BASE_URL` | Явный адрес OpenAI-совместимого API | Для `index-context` и `run` |
| `EMBEDDING_MODEL` | Модель embeddings | Для индексации и поиска |
| `MAIL_AGENT_DATABASE_PATH` | Путь к SQLite | Необязательно, default `mail_agent.sqlite3` |
| `MAIL_AGENT_CHROMA_PATH` | Путь к ChromaDB | Необязательно, default `chroma_data` |

Настройка для проверенного локального сценария:

```bash
export LLM_API_KEY=ollama
export LLM_MODEL=qwen3:8b
export LLM_BASE_URL=http://localhost:11434/v1
export EMBEDDING_MODEL=embeddinggemma
export MAIL_AGENT_DATABASE_PATH=mail_agent.sqlite3
export MAIL_AGENT_CHROMA_PATH=chroma_ollama
```

Для облачного OpenAI endpoint задаётся явно:

```bash
export LLM_API_KEY="<ваш API-ключ>"
export LLM_MODEL="<модель с Responses API и function calling>"
export LLM_BASE_URL=https://api.openai.com/v1
export EMBEDDING_MODEL=text-embedding-3-small
export MAIL_AGENT_CHROMA_PATH=chroma_data
```

Облачный OpenAI API в рамках приёмки не вызывался. Не сохраняйте реальный ключ
в Git, README или истории команд. `.env.example` является только образцом:
приложение не загружает `.env` автоматически. При использовании файла загрузите
переменные в текущий Git Bash самостоятельно или выполните команды `export`.

Справка и `init-db` не требуют API-настроек и не выполняют внешних обращений:

```bash
mail-agent --help
mail-agent init-db
```

## Подготовка данных

### SQLite

```bash
mail-agent init-db
```

Команда создаёт схему и загружает вымышленные цепочки из `data/emails.json`.
Повторный запуск не перезаписывает письма. Если база содержит неполный или иной
набор, команда завершается ошибкой без удаления данных.

### Индексация контекста

```bash
mail-agent index-context
```

Индексируются все демонстрационные письма и четыре документа:

- `product_catalog.md`;
- `delivery_terms.md`;
- `payment_terms.md`;
- `client_communication.md`.

При смене `EMBEDDING_MODEL` или алгоритма chunking существующая коллекция
считается несовместимой. Для явной полной переиндексации:

```bash
mail-agent index-context --recreate
```

`--recreate` удаляет существующую коллекцию. Операция неатомарна: при ошибке API
после удаления прежний индекс автоматически не восстанавливается.

## Запуск агента

### Поиск, чтение и сводка

```bash
mail-agent run --diagnostics \
  "Найди через search_emails переписку о насосах НЦ-80. Определи нужную цепочку, прочитай её через read_thread и составь краткую сводку согласованных условий оплаты с источниками. Черновик не создавай."
```

Диагностика выводит в `stderr` только безопасные счётчики, разрешённые имена
инструментов, успешность и категории ошибок. Аргументы, письма, RAG-контекст,
системный промпт, canary и полные ответы модели не выводятся.

Если `thread_id` уже известен, предварительный поиск не обязателен:

```bash
mail-agent run \
  "Прочитай через read_thread цепочку thread-003 и подготовь сводку подтверждённых условий оплаты с источниками."
```

### Создание черновика

```bash
mail-agent run --allow-draft --diagnostics \
  "Прочитай через read_thread цепочку thread-003 и подготовь клиенту черновик ответа по согласованным условиям оплаты."
```

`--allow-draft` является явным разрешением менеджера на сохранение черновика в
текущем запуске. Без флага Python-код запрещает `create_draft` независимо от
решения LLM. Письмо сохраняется, но никогда не отправляется.

Результат содержит:

```text
Сводка:
<содержательный ответ>

thread_id: <проверенный ID цепочки>
source_ids:
- <ID письма или документа>
draft_status: <not_authorized | not_created | created>
draft_id: <фактический UUID только при created>
```

Проверить сохранённые черновики можно без их отправки:

```bash
python -c "import sqlite3; connection = sqlite3.connect('mail_agent.sqlite3'); print(connection.execute('SELECT draft_id, thread_id, recipient, subject, created_at FROM draft_replies ORDER BY created_at DESC').fetchall()); connection.close()"
```

Текст модели не считается подтверждением сохранения. `draft_status=created` и
`draft_id` формируются только после фактической записи UUID в SQLite.

## Почтовые инструменты

Модели доступны ровно три внешних инструмента:

- `search_emails(query, sender, date_from, date_to, limit)` — поиск писем по
  словам, отправителю и диапазону дат;
- `read_thread(thread_id)` — полная цепочка в хронологическом порядке;
- `create_draft(thread_id, recipient, subject, body)` — сохранение черновика в
  SQLite без отправки.

Инструмента `send_email` нет.

Этапы доступности:

1. До чтения цепочки доступны `search_emails` и `read_thread`.
2. После успешного `read_thread` Python обязательно выполняет RAG.
3. После RAG при `--allow-draft` доступен только `create_draft`.
4. После успешного создания инструменты больше не предлагаются, и модель
   формирует содержательный ответ.

Если модель после поиска не вызывает `read_thread`, Python даёт одно
контролируемое напоминание, затем завершает запуск детерминированной ошибкой.

## RAG и проверяемые источники

```text
SQLite-письма + Markdown-документы
                  ↓
       embeddinggemma через Ollama
                  ↓
      ChromaDB, cosine, общий top-k
                  ↓
read_thread → обязательный RAG → сводка/черновик
```

- максимальный размер chunk — 2000 символов вместе с заголовками;
- overlap — 200 символов;
- `DEFAULT_TOP_K = 5`;
- `MAX_CONTEXT_DISTANCE = 0.75` — начальный экспериментальный порог;
- неизменённые источники пропускаются по SHA-256;
- письма индексируются с `source_id`, `thread_id`, `date`,
  `source_type=email`;
- документы имеют `source_type=document` и доступны всем цепочкам;
- при выбранной цепочке поиск допускает только её email-фрагменты и все общие
  документы;
- дубликаты `chunk_id` исключаются;
- `source_ids` строятся Python-кодом из прочитанной цепочки и результатов RAG.

ID источников предназначены для менеджера. Они не должны попадать в текст
клиентского черновика. Пустой RAG не отменяет факты из прочитанной цепочки, но
при отсутствии данных агент должен сообщить об их недостаточности.

## CanaryGuard и журнал безопасности

Для каждого `MailAgent.run()` создаётся новый криптографически случайный canary.
Один токен действует на все ответы LLM текущего запуска.

```text
LLM response
     ↓
CanaryGuard
     ├─ безопасно → Python-обработка → инструмент или результат
     └─ CANARY_MATCH → одно событие JSONL → нейтральный ответ → остановка
```

До выполнения любого инструмента проверяются текст, отказ, reasoning,
`output_items`, сырой JSON и исходные/декодированные/вложенные аргументы function
calls. Решение о блокировке принимает только Python-код.

`security_events.jsonl` находится в корне и исключён из Git. Событие содержит
только:

- `timestamp` в UTC;
- `run_id`;
- `location`;
- `reason=CANARY_MATCH`;
- `action=BLOCKED`;
- `event_type=SYSTEM_PROMPT_LEAK`.

Токен, системный промпт, ответ модели, аргументы, API-ключи и traceback в журнал
не записываются. При ошибке записи выполнение остаётся заблокированным.

CanaryGuard ищет полное точное вхождение токена. Он не гарантирует обнаружение
пересказа системного промпта, преобразованного токена или всех prompt injection
атак.

## Три угрозы вследствие утечки системного промпта

Ниже приведена модель угроз, а не результаты выполненных атак. Утечка может
произойти при прямом запросе к модели либо через prompt injection в письме или
справочном документе. Действующие механизмы описывают текущую реализацию;
дополнительные меры являются рекомендациями для дальнейшего усиления.

### 1. Адресная атака на почтовые инструменты

- **Раскрываемые сведения:** названия и назначение `search_emails`,
  `read_thread` и `create_draft`, необходимость прочитать выбранную цепочку и
  выполнить RAG, а также правила подготовки, сохранения и ограничения
  клиентских черновиков. Полные JSON-контракты и детали Python-валидации в
  системном промпте не описаны.
- **Способ получения:** злоумышленник побуждает модель вывести системные
  инструкции напрямую, пересказать их по частям либо поместить их в ответ через
  инструкцию внутри недоверенного письма или документа.
- **Использование:** зная имена инструментов и обязательную
  последовательность, атакующий может подготовить адресную инъекцию, которая
  побуждает модель выбрать нужный ему инструмент и предложить `create_draft` с
  навязанным текстом, цепочкой или адресатом.
- **Последствия:** попытка создать вводящий клиента в заблуждение черновик,
  связать его с неверной перепиской или направить стороннему получателю. Это
  может привести к ошибочной коммуникации и репутационному ущербу.
- **Действующая защита:** Python независимо проверяет этап работы,
  `--allow-draft`, выбранный `thread_id`, обязательный RAG и получателя; отправки
  писем нет. Знание системного промпта само по себе эти проверки не отключает.
- **Дополнительная мера:** перед сохранением чувствительных черновиков требовать
  отдельное подтверждение менеджера с показом цепочки и получателя, а также
  вести безопасный аудит разрешённых операций без текста писем и секретов.

### 2. Обход детектирования утечки

- **Раскрываемые сведения:** активный canary-токен и прямой запрет раскрывать,
  повторять, преобразовывать или косвенно восстанавливать его и системные
  инструкции. Поиск полного совпадения, проверяемые поля и порядок блокировки
  определены в Python-коде, а не в системном промпте.
- **Способ получения:** модель может раскрыть токен или запрет при прямом запросе
  системных инструкций либо при инъекции, требующей повторить, преобразовать или
  пересказать скрытый текст.
- **Использование:** получив токен или узнав о запрете, атакующий может пробовать
  пересказ, разбиение на части, кодирование или иное преобразование скрытого
  текста. Такое использование нацелено на обход точного совпадения, механизм
  которого реализован отдельно в Python-коде.
- **Последствия:** частичное раскрытие внутренних политик и контрактов повышает
  точность последующих атак, хотя событие `CANARY_MATCH` может не возникнуть.
- **Действующая защита:** CanaryGuard до любой обработки проверяет полный ответ,
  сырой JSON и вложенные аргументы; при точном совпадении блокирует весь запуск и
  пишет одно безопасное событие. Python-ограничения инструментов действуют даже
  при утечке текста промпта.
- **Дополнительная мера:** добавить отдельный детектор семантического раскрытия
  инструкций и преобразованных секретов, а также регулярно проводить red-team
  проверки с дроблением, кодированием и пересказом промпта.

### 3. Целевое отравление RAG-контекста

- **Раскрываемые сведения:** использование внутреннего RAG по прочитанной
  переписке и справочным документам, обязательность RAG перед сводкой или
  черновиком и недоверенный статус найденного содержимого. Chunking, overlap,
  cosine, top-k и числовые пороги в системном промпте не указаны.
- **Способ получения:** злоумышленник извлекает описание RAG из утёкших
  системных инструкций напрямую либо через последовательные вопросы к модели.
- **Использование:** зная, какие типы источников попадают в контекст, он может
  внедрить в доступное письмо или справочный документ ложные сведения и
  инструкции, рассчитывая на их попадание в RAG и влияние на итоговый текст.
- **Последствия:** модель может сильнее опираться на навязанный контекст,
  представить одностороннее предложение как договорённость или подготовить
  неверные условия оплаты и поставки для клиента.
- **Действующая защита:** письма и документы помечаются недоверенными; email-RAG
  ограничен выбранной цепочкой; Python проверяет `source_ids`; системный промпт
  запрещает выдумывать договорённости и требует сообщать о противоречиях.
- **Дополнительная мера:** разрешать индексацию справочных документов только из
  контролируемого хранилища с проверкой автора и целостности, а при ранжировании
  учитывать уровень доверия к источнику и отправлять спорные условия на ручную
  проверку менеджеру.

## Выполненные проверки

Автоматические тесты используют временные SQLite/ChromaDB, детерминированные
тестовые embeddings и синтетические LLM-ответы. Они не вызывают Ollama или
платный OpenAI API.

```bash
ruff check .
ruff format --check .
pytest -p no:cacheprovider
```

После нейтрального переименования конфигурации проходят 137 тестов.

На реальной Ollama с `qwen3:8b` и `embeddinggemma` вручную подтверждены:

1. `search_emails → read_thread → RAG → сводка`;
2. `read_thread → RAG → create_draft → SQLite`, причём UUID результата совпал
   с записью базы;
3. при работе с `thread-003` email-фрагмент `email-003` другой цепочки не попал
   в RAG;
4. внутренние ID источников не попали в сохранённый клиентский черновик.

### Краткие примеры фактически проверенных результатов

Сводка по насосам:

```text
pipeline: search_emails → read_thread → RAG → summary
thread_id: thread-003
verified email sources: email-006, email-007
isolation check: email-003 отсутствует
result: 50% авансом, 50% после уведомления о готовности;
        срок действия счёта — пять банковских дней
```

Черновик клиенту:

```text
pipeline: read_thread → RAG → create_draft → SQLite
draft_status: created
draft_id: <значение скрыто; UUID совпал с записью draft_replies в SQLite>
result: сохранён черновик с условиями оплаты, запросом реквизитов и сроком счёта
```

В примерах не публикуются текст переписки, системный промпт, canary, API-ключи
или фактический UUID черновика.


## Известные ограничения

- Решение предназначено для локального однопользовательского запуска.
- Один `LLM_BASE_URL` и ключ используются для LLM и embeddings; гибрид локальной
  LLM с embeddings другого провайдера не поддерживается.
- Совместимость function calling зависит от OpenAI-совместимости локальной
  модели; Python останавливает циклы без прогресса и множественные tool calls.
- `MAX_CONTEXT_DISTANCE = 0.75` требует калибровки на реальных данных.
- CanaryGuard не обнаруживает все утечки и prompt injection атаки.
- Полная переиндексация ChromaDB неатомарна.
- Standalone wheel не включает внешние `data/` и `prompts/`; поддержан запуск из
  исходного репозитория через editable install.
- Письма не отправляются, а сохранённые черновики требуют проверки менеджером.
